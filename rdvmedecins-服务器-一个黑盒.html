    7. RdvMedecins 服务器，一个黑盒

    示例 22 至 25 以及案例研究都与一个服务器交互：即[RdvMedecins]应用的 JSON 服务器。它就是上一课中的[NestJS]服务器，其控制器不再生成 HTML 页面，而是生成 JSON 响应。它的业务层和数据访问层保持不变。

    在本课程中，这个服务器是一个黑盒：我们无需知道它是如何编写的。重要的只是它的API——也就是它接受的 HTTP 请求列表以及它返回的响应。这是客户端开发人员的典型处境：API 是一份契约，服务器团队可以在这份契约背后随意更改任何内容。对于好奇的读者，我们提供了它的源代码（[rdvmedecins-nestjs-json]文件夹），并附有详尽的注释。

    本章说明如何安装该服务器，描述其 API，并使用[curl]对其进行查询。

    7.1. RdvMedecins 应用

    该应用用于管理一家医疗诊所的预约。它有三种角色：

    角色
    对象
    可执行的操作
    [ADMIN]
    管理员（[admin]）
    为所有患者安排和取消预约；管理医生和客户
    [DOCTOR]
    医生（[pelissier]、[tatou]、[dupont]）
    为所有患者安排和取消预约；在日历中查看所有姓名
    [USER]
    患者（[martin]、[durand]、[bistrou]、[german]）
    为自己预约；取消自己的预约；管理自己的账户。在日历中，他们看不到其他患者的姓名

    演示账户使用其登录名作为密码。管理规则由服务器验证，与客户端无关：

    • 不允许预约过去的时间；
    • 每位患者只能有一个即将到来的预约；
    • 同一时间段每天只能被预约一次；
    • 两位医生（或两位客户）不能拥有相同的姓和名；一个登录名只属于一个账户；
    • 有预约的医生不能被删除；
    • 在此期间已被他人修改的记录不能被覆盖（乐观锁）；
    • 患者绝不会被分配到另一位患者的姓名。

    7.3. 响应格式

    所有 URL 都以[/api]开头。成功的请求会收到 2xx 状态码，并在响应体中收到 JSON 格式的所请求数据。被拒绝的请求会收到 4xx 或 5xx 状态码，并在响应体中收到同样格式的数据：

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "key": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "fields": { "lastName": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode]：HTTP 状态码，在响应体中重复出现；
    • [key]：消息的翻译键。服务器从不返回要显示的文本：它不再知道用户的语言。由客户端使用其字典翻译该键（参见示例 21）；
    • [params] （可选）：消息参数（[At least {min} characters], [Try again in {minutes} minute(s)]）；
    • [fields] （可选）：对于被拒绝的表单，给出每个字段的错误。

    使用的状态码：

    状态码
    含义
    键的示例

    [ERRORS.INVALID_FORM] （+ fields）、[ERRORS.INVALID_DATE]、[ERRORS.WRONG_CAPTCHA]、[ERRORS.CHOOSE_PATIENT]、[ERRORS.WRONG_CURRENT_PASSWORD]、[ERRORS.BAD_REQUEST]……

    7.4. 身份验证

    客户端使用[POST /api/auth/login]进行身份验证，提交用户名、密码和验证码答案。作为回应，服务器会在浏览器中放置一个Cookie，其中包含已签名的 JWT 令牌：

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; HttpOnly; SameSite=Strict

    它的属性对安全性很重要：

    • [HttpOnly]：页面的[JavaScript]代码无法读取此 Cookie。因此，注入页面的恶意脚本无法窃取令牌。对客户端的影响是：它无法自行判断是否已登录，而要询问服务器（[GET /api/auth/me]）；
    • [Path=/api]：浏览器仅在发往 API 的请求中携带它；
    • [SameSite=Strict]：浏览器仅在从此站点的页面发出的请求中携带该令牌。另一个站点上的恶意页面无法让浏览器代表用户执行操作（即所谓的 CSRF 攻击）；
    • [Max-Age=7200]：它在两小时后过期，与令牌的过期时间一致。

    此后，浏览器会在发往[/api]的每个请求中自动发送这个 Cookie。因此，只要页面和 API 共享[Angular] 客户端的同源 （相同的协议、相同的机器、相同的端口），客户端就无需做任何事情来验证自己的身份。这就是[Angular]开发服务器上代理的作用（参见示例 22），在生产环境中则由服务器自身承担（参见“部署”一章）。

    针对 CSRF 攻击的第二重保护：服务器会拒绝（415）任何请求体不是 JSON 的 POST 请求。其他站点上被篡改的 HTML 表单无法发送 JSON。

    7.6. 使用 curl 查询 API

    服务器上的 [curl] 文件夹包含本章使用的 JSON 请求体，每个请求一个文件。例如 [curl/login-admin.json]：

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    命令在打开于 [rdvmedecins-nestjs-json] 目录的控制台中输入。[curl] 的一些选项：

    • [-i]：同时显示响应头；[-s]：不显示进度条；
    • [--json @file]：以 POST 方式发送文件内容，并带有请求头 [Content-Type: application/json] （curl 7.82 及更高版本；如果是旧版本，请使用 [-H "Content-Type: application/json" -d @file]）；
    • [-X PUT]、[-X DELETE]：HTTP 方法；
    • [-c cookies.txt]：将收到的 Cookie 保存到该文件；[-b cookies.txt]：将它们发回。[curl] 就是这样在一条命令到下一条命令之间“保持登录”的，和浏览器的做法一样。

    在 [PowerShell] 下，必须输入 [curl.exe] 而不是 [curl] （在那里它指的是另一条命令）。为便于阅读，本文档对较长的 JSON 响应做了格式化，并去掉了 [Date]、[ETag]、[Connection]、和 [Keep-Alive] 这几个响应头。
